📝 Overview

The Industrial Air Quality Monitor is a compact embedded system built around the Arduino Nano that measures several airborne parameters relevant to industrial environments — including particulate matter, gas concentration, temperature, and humidity — and raises an alert when any reading crosses a pre-set safety threshold. The project was developed as an educational prototype to demonstrate how low-cost open-source hardware can be assembled into a serious monitoring instrument suitable for workshops, factory floors, storage rooms, or any space where airborne contaminants can affect worker safety or product quality.

What makes this repository different from a typical Arduino demo is the documentation discipline behind it. Every sensor in the build has its operating range, calibration expectations, and known limitations written down so that a reader can decide whether the prototype is suitable for their own context. Threshold values are clearly marked as configurable and the alert logic is split out from the sensing logic so that the same firmware can be reused across different sensor combinations without rewriting the core flow. This makes the project a starting point that can be adapted to gas-specific hazards (CO, CO₂, VOC, dust) rather than a one-off build that only runs on a workbench.

The system is intended as an educational demonstration, not a certified industrial safety instrument. It is suitable for student labs, learning projects, and proof-of-concept deployments. Anyone who needs to deploy air-quality monitoring in a regulated industrial environment should use certified, calibrated commercial instruments and follow local occupational health and safety regulations.

🔭 Background

In industrial environments, airborne hazards are among the most difficult risks to manage because they are invisible and accumulate gradually. Workers may be exposed to elevated levels of particulate matter, hazardous gases, or simply to environments where temperature and humidity drift outside a safe band — and there is often no obvious warning until symptoms appear. A small, low-cost monitoring device placed in the right location can provide an early warning that protects both people and equipment, but most commercial options are either too expensive for distributed deployment or too opaque to adapt.

This project was built to address two practical gaps at the same time: first, the need for a low-cost, visible, and audible warning when air quality crosses a threshold; second, the need for a documented, repeatable build that an electrical technology student can read end-to-end and understand. By keeping the firmware modular and the documentation honest about sensor limitations, the repository supports both goals without overpromising what hobby-grade sensors can actually deliver.

✨ Key Features

  • Multi-sensor air-quality monitoring — integrates gas, particulate, temperature, and humidity sensors on a single Arduino Nano, with each sensor polled on its own recommended interval. The design intentionally separates the sensing layer from the alerting layer so that swapping sensors only requires updating the relevant module, not rewriting the main loop.
  • Threshold-based alert system — every measured parameter has a configurable safe range defined in a single configuration section at the top of the firmware. When any reading falls outside its safe range, the system triggers a visible (LED) and audible (buzzer) alarm. Thresholds can be tuned for different environments without modifying the alert logic itself.
  • Real-time serial output — all sensor readings are written to the serial monitor in a simple key:value format, making it easy to log readings, plot trends, or pipe the data into a PC-side dashboard for further analysis. The format is intentionally human-readable so that troubleshooting does not require a custom tool.
  • Modular firmware structure — the codebase is split into clearly named modules (sensor drivers, threshold configuration, alert manager, main loop) rather than a single monolithic .ino file. This keeps the firmware readable and makes it straightforward to extend the system with new sensors or different output channels (LCD, Wi-Fi, SD card logging).
  • Compact, low-power build — designed around the Arduino Nano so the full system fits in a small enclosure and can be powered from a standard 5 V USB source or a 7–12 V DC adapter. This makes it practical to deploy in multiple rooms without significant wiring work.

The architecture follows a sense → check → alert pipeline. Each sensor module produces a reading on its own cadence, hands it to the threshold checker, which compares it against the configured safe range, and the alert manager decides whether to raise, hold, or clear the alarm. Serial output runs in parallel so the user always sees the live readings regardless of alarm state. This separation is the key to the firmware's reusability: a different sensor only changes the first block, a different alarm mechanism only changes the last block.

🚀 Getting Started

Prerequisites

  • Arduino IDE 1.8.13 or newer (or Arduino CLI)
  • Arduino Nano board (or compatible clone with the same MCU)
  • USB cable for programming and serial monitoring
  • Sensors listed in Hardware Components above

Installation

  1. Clone the repository
    bash git clone https://github.com/nicksananton0923-create/industrial-air-quality-monitor.git cd industrial-air-quality-monitor

  2. Open the firmware in Arduino IDE
    - Open firmware/air_quality_monitor.ino in the Arduino IDE.
    - From Tools → Board, select Arduino Nano.
    - From Tools → Processor, select the matching variant (e.g. ATmega328P).
    - From Tools → Port, select the USB port the Nano is connected to.

  3. Install required libraries
    - Use Sketch → Include Library → Manage Libraries and install any libraries referenced in the firmware (e.g. the DHT sensor library by Adafruit).

  4. Wire the sensors following the wiring guide in docs/wiring-guide.md.

  5. Upload the firmware and open the Serial Monitor at the baud rate declared at the top of the sketch (default 9600).

🎯 Usage

Once the firmware is uploaded and the sensors are wired, the monitor runs autonomously. The default operating loop is:

  1. Each sensor is polled on its recommended interval (e.g. DHT22 every 2 seconds, PM sensor every 1 second).
  2. Readings are printed to the serial monitor in key:value format.
  3. Each reading is compared to its configured threshold.
  4. If any reading breaches its threshold, the LED turns red and the buzzer pulses.
  5. When all readings return to safe range, the alarm clears and the LED returns to green.

To customize thresholds, edit the configuration block at the top of air_quality_monitor.ino:

// === Threshold configuration ===
const float PM25_MAX   = 35.0;   // µg/m³
const float PM10_MAX   = 75.0;   // µg/m³
const float GAS_MAX    = 400.0;  // ppm (sensor-specific)
const float TEMP_MIN   = 15.0;   // °C
const float TEMP_MAX   = 35.0;   // °C
const float HUM_MIN    = 30.0;   // %
const float HUM_MAX    = 70.0;   // %

⚠️ Safety & Compliance Notes

  • Educational use only. This device is not a certified industrial safety instrument. Do not use it as the sole means of hazard detection in a regulated environment.
  • Sensor calibration. MQ-series gas sensors require warm-up time and periodic calibration. Readings from these sensors are indicative, not laboratory-grade. Always cross-check against a calibrated reference instrument before relying on the numbers.
  • Threshold tuning. Default thresholds are illustrative. Real industrial deployments should follow the workplace exposure limits published by the relevant occupational health authority in your jurisdiction.
  • Power safety. Use a properly rated power supply. For continuous deployment, prefer a regulated 5 V DC source over USB power from a PC.

📝 Overview

The Industrial HVAC Maintenance repository is a complete documentation framework for organizing and managing maintenance work on industrial heating, ventilation, air-conditioning, and cooling systems. It contains reusable CSV templates for every common record a building-services team needs — asset registers, chiller service records, AHU inspection checklists, cooling-tower logs, fault and corrective action logs, preventive maintenance schedules, and more — alongside Markdown documentation that explains the purpose of each field, the methodology behind each inspection, and how the templates fit into a coherent maintenance program.

This is not a software project in the traditional sense; it is a structured set of files that an HVAC maintenance team, a building services manager, or a student of facility engineering can drop into a shared folder and start using immediately. The templates are deliberately vendor-neutral and use plain column names so they open cleanly in Excel, Google Sheets, LibreOffice Calc, or any CSV-aware tool. Every record includes clear field descriptions, sensible defaults, and explicit notes on which fields are mandatory versus optional, which makes them easy to onboard for new technicians without long training sessions.

The repository is being built incrementally — every file that exists is already production-useful, and every file that is still on the roadmap is explicitly called out in the Roadmap section. Nothing in this repository should be considered final until it has been reviewed by a qualified maintenance engineer for the specific equipment and jurisdiction in which it will be used.

🔭 Background & Motivation

Industrial HVAC systems — chillers, air handling units, cooling towers, pumps, fans, and the control networks that tie them together — represent some of the most expensive and most failure-prone equipment in any modern building. A single chiller failure can take an entire process plant offline; a single poorly documented AHU inspection can mean a filter is replaced a month late, an indoor-air-quality complaint is dismissed, or a bearing fails without warning. The cost of these events is almost always higher than the cost of the documentation that would have prevented them.

And yet, in many facilities, maintenance records are scattered: some live on paper, some live in spreadsheets, some live in the heads of senior technicians, and some are not recorded at all. The result is that when a technician leaves, knowledge walks out the door; when an audit arrives, no one can prove what was inspected and when; and when a fault recurs, no one can trace whether the same fault has been seen before. This repository was built to provide a simple, reusable starting point for fixing that gap. It does not replace a full CMMS, but it gives a team a structured, vendor-neutral place to start collecting records in a consistent format — which is the first step toward any future digital system.

🎯 How to Use the Templates

  • One row per record. Each CSV is structured so one row represents one event (one inspection, one service, one fault). This keeps the data tidy and easy to filter or chart.
  • Asset IDs are sacred. Use the same asset ID across every CSV so records can be joined. The asset register is the source of truth for what each ID means.
  • Units must be explicit. Every numeric field has a documented unit in recordkeeping-guide.md. Never write a number without a unit, and never mix units in the same column.
  • Dates are ISO 8601. Use YYYY-MM-DD for all dates so the CSVs sort and filter correctly across locales.
  • Technician and signature. Every record has a technician column and (where applicable) a reviewed_by column. Accountability is the whole point.

⚠️ Safety & Accuracy

  • Refrigerant handling must be done by certified personnel. The refrigerant-service-log.csv template is for record-keeping only — filling it in does not authorize anyone to handle refrigerants.
  • HVAC electrical work is hazardous. Any template that includes electrical readings assumes the work is being done by a qualified electrician or technician.
  • OEM manuals override these templates. Equipment-specific limits, service intervals, and procedures from the OEM manual always take precedence. These templates are vendor-neutral; they cannot capture every model-specific requirement.
  • Confidentiality. Never commit real facility readings, customer names, or proprietary information to a public repository. Use the sample-records.csv pattern as a guide for anonymizing your own data.

📝 Overview

The Industrial Maintenance Request System is a lightweight Computerized Maintenance Management System (CMMS) designed for small and medium industrial facilities that need a structured way to handle maintenance work requests without investing in a heavy enterprise platform. The system covers the full lifecycle of a maintenance task: a worker submits a request, a supervisor reviews and approves it, a technician is assigned, the work is carried out and documented, the work order is closed, and the resulting record is archived for future reporting and audit. Every step is logged so that the team can later answer questions such as "how long did this fault take to close?", "which technician closed the most work orders last month?", or "which asset is generating the most repeat requests?".

The project is built in JavaScript because the front-end needs to be approachable for any team member to use on a phone, tablet, or laptop, and because the underlying data model is simple enough that a heavier stack would add more complexity than value. The interface focuses on clarity over feature density: a maintenance technician opening the system on a phone in a noisy plant room should be able to see exactly what is assigned to them today and update a work order status with two taps, not navigate a multi-level menu.

This repository is being built incrementally, with the data model and core workflow documented first and the user interface layers added on top. Every planned feature is listed in the Roadmap so that readers can see what already works and what is still in progress. Nothing in the system should be considered production-ready until it has been reviewed for the specific facility where it will be deployed, including any required access controls, backups, and integration with existing site systems.

🔭 Background

In most small industrial facilities, maintenance requests flow through some combination of paper forms, phone calls, WhatsApp messages, and whiteboards. Each of those channels has the same fundamental problem: there is no structured record. A technician who receives a request by phone has no written record of what was requested, by whom, when, with what priority, or against which asset. When the same fault recurs a month later, no one can easily discover that it has been seen before. When a new technician joins the team, they have no documented history to learn from. When the facility manager is asked "how many breakdowns did we have last quarter?", the answer is usually a guess.

A lightweight CMMS solves this by providing a single place where every maintenance request becomes a structured record. The request captures who asked, what they asked for, which asset is affected, how urgent it is, and when it was reported. The record then flows through a defined lifecycle — approved, assigned, in progress, completed, closed — with each transition logged with a timestamp and the responsible person. This gives the team an audit trail, a learning base, and a reporting surface that none of the ad-hoc channels can provide. 📝 Overview

The Smart Fire Detection & Suppression System is an Arduino-based prototype designed to demonstrate how embedded electronics can be used to detect the early signs of a fire and trigger an automated safety response. The project combines multiple flame and smoke sensors with control logic that decides when to raise an alarm and when — conceptually — to activate a suppression mechanism such as a water spray, a CO₂ release, or an extinguisher trigger. The system is built as an educational demonstration of fire sensing, emergency alerting, and automated safety control; it is not a commercial fire suppression product.

The repository documents the prototype end-to-end: the sensor choices and their limitations, the control logic that fuses multiple sensor inputs to reduce false alarms, the alarm path (visual + audible + remote alert), and the conceptual suppression path that explains how the same logic would interface with a relay-actuated extinguisher in a real deployment. The threshold logic is intentionally separated from the actuation logic so that the same firmware can be reused with different sensor combinations or different suppression endpoints without rewriting the decision core.

For students and educators, the project provides a clean, well-documented example of how to design a safety-critical embedded system the right way: every assumption is written down, every threshold is configurable, and every limitation is explicitly called out so that the reader can make an informed decision about adapting the work to their own context.

🔭 Background

Fire is one of the most time-critical hazards in any industrial or domestic environment. The difference between a near-miss and a serious incident often comes down to seconds — how quickly the fire is detected, how reliably the alarm is raised, and whether the suppression response starts before the fire has had time to spread. Traditional smoke detectors are excellent for homes but limited in industrial environments where dust, fumes, or heat variations can trigger false alarms. A multi-sensor approach that combines flame detection, smoke detection, and temperature sensing produces a more reliable decision than any single sensor on its own.

This project was built to demonstrate that multi-sensor approach in a way that is reproducible by an electrical technology student. The prototype uses a flame sensor for direct flame detection, a smoke / gas sensor for early combustion products, and a temperature sensor for ambient heat rise. The firmware fuses these three signals using a simple voting system — at least two of the three sensors must agree that a fire condition exists before the alarm escalates — which dramatically reduces false positives from a single noisy sensor while still responding quickly to a real fire event.

✨ Key Features

  • Multi-sensor fire detection — combines a flame sensor (IR-based), an MQ smoke / gas sensor, and a temperature / humidity sensor. Each sensor contributes one vote to the decision core, so a single noisy reading does not trigger a false alarm. This voting approach mirrors the redundancy used in professional fire detection panels.
  • Threshold-based decision core — every sensor has a configurable threshold defined at the top of the firmware. The decision logic compares each reading to its threshold, counts how many sensors are in alarm state, and escalates only when the configured minimum number of sensors agree (default: 2 of 3). This makes the system robust against false positives from a single sensor.
  • Three-stage alarm — when a fire condition is detected, the system raises a visual alarm (red LED + status indicator), an audible alarm (piezo buzzer), and a remote alert output (relay or digital output) that can be wired to a wider alarm system. The remote output is what would interface with a suppression actuator in a real deployment.
  • Conceptual suppression path — the firmware includes a commented-out suppression module that demonstrates how a relay-actuated extinguisher or water spray would be triggered after a configurable delay. The module is intentionally left inactive in the educational build so that no high-current actuator is energized during classroom demonstrations.
  • State-machine firmware structure — the main loop is structured as a small explicit state machine (IDLE → DETECT → ALARM → (optional) SUPPRESS → COOLDOWN → IDLE) rather than a tangled if/else chain. This makes the control flow easy to read in a classroom setting and easy to extend with new states.
  • Full documentation — every sensor, every threshold, and every assumption is written down. The documentation explicitly states what has been tested versus what remains conceptual so that anyone adapting the project knows exactly where the boundaries of the prototype are.

📝 Overview

The Tomato Colour Sorting Conveyor is an Arduino-based automation project that detects the ripeness of a tomato using a colour sensor, classifies it into one of three categories — green, partially ripe, or red — and uses a servo-driven diverter to push each tomato into the correct bin as it travels along a small conveyor belt. The project demonstrates how affordable embedded hardware can be assembled into a complete sensing-and-actuation pipeline suitable for small-scale agricultural grading, classroom demonstrations of industrial automation, and proof-of-concept workflows for produce handling.

The repository documents the full build, including the colour sensor selection and calibration approach, the conveyor mechanism, the servo-actuated sorting gate, and the firmware that ties everything together. The classification logic is intentionally simple and explainable: the firmware reads red / green / blue component values from the colour sensor, computes a single ripeness score, and classifies against two configurable thresholds. This keeps the logic transparent so a reader can audit it end-to-end, while still being flexible enough that the same firmware can be retuned for other produce (oranges, bananas, capsicum) by changing the calibration constants.

The project is built as an educational prototype and is not intended for production-scale commercial packing. It is suitable for student lab work, science fairs, and concept demonstrations in agricultural automation courses. As with the other repositories on this account, every assumption and every limitation is written down so that the next reader can adapt the work safely and confidently.

🔭 Background

Manual sorting of produce by ripeness is slow, inconsistent, and labor-intensive. In a small-scale operation — a farm gate, a cooperative packing shed, or a teaching kitchen — there is rarely a budget for an industrial vision system, but there is a real need for a low-cost, repeatable way to separate ripe from unripe produce so that each batch goes to the right destination (immediate sale, ripening storage, or processing). Colour is one of the simplest and most reliable signals for tomato ripeness, which makes a colour-sensor-based sorter an ideal first automation project for an agricultural technology course.

The build sits at a useful intersection of three learning areas: embedded sensing (calibrating a colour sensor against real-world produce), mechanical actuation (timing a servo gate so the right tomato lands in the right bin), and control logic (deciding when to read the sensor, when to actuate the gate, and how to handle the belt's continuous motion). Each of those three layers is documented separately in this repository so the project can be used as a teaching tool for any one of those topics in isolation, not only as a complete system.

✨ Key Features

  • RGB colour sensing — uses a TCS3200 (or compatible) colour sensor to read the red, green, and blue components of each tomato as it passes the sensor station. The firmware averages a small number of readings to reduce noise from a single sample.
  • Three-class ripeness classification — each reading is reduced to a single ripeness score and classified against two configurable thresholds into green, partially ripe, or red. The thresholds live in a configuration block at the top of the firmware so they can be retuned without touching the classification logic.
  • Servo-driven sorting gate — a single servo rotates a diverter gate to one of three positions corresponding to the three ripeness bins. The firmware controls the gate timing relative to the conveyor speed so the right tomato lands in the right bin even when the belt is moving.
  • Belt speed awareness — the firmware uses a configurable belt-speed parameter (and optionally an IR slot sensor) to time the delay between the colour reading and the servo actuation, so the sorting decision is applied to the correct tomato rather than the one immediately after it.
  • Serial diagnostics — every reading, classification decision, and servo movement is written to the serial monitor in a simple human-readable format, so the system can be tuned and debugged without any external tooling.
  • Modular firmware structure — the codebase is split into clearly named modules (colour reader, classifier, servo driver, conveyor timing) rather than a single monolithic sketch, so each layer can be tested and replaced independently.

🎨 Calibration & Tuning

  • Ambient light matters. The TCS3200 is sensitive to ambient light. Shield the sensor station with a small opaque hood and use the sensor's onboard LED for consistent illumination.
  • Sample several tomatoes per class. Single-sample calibration is unreliable. Take 5–10 readings per ripeness class and use the average.
  • Servo timing depends on belt speed. If you change the conveyor motor speed, recalibrate SENSOR_TO_GATE_MS empirically by running a known tomato through the system and observing which bin it lands in.
  • Mechanical alignment. The diverter gate must reach its target position before the tomato arrives. If the gate is still moving when the tomato arrives, the tomato will be deflected incorrectly.

  • Mechanical safety. Moving belts and servo-driven gates can pinch fingers. Use a transparent cover over the gate mechanism during demonstrations.
  • Power supply. A servo under load can draw bursts of current that crash the Arduino. Always use a separate 5 V supply for the servo and tie the grounds together.
  • Sensor limits. The colour sensor cannot see through packaging, dirt, or uneven tomato surfaces. Sort washed, unpacked tomatoes for best results.
  • Not for production. This is an educational prototype. Production-scale sorters use machine vision, multi-sensor fusion, and food-grade materials. This project does not replace them.

📝 Overview

The Industrial Water Consumption Monitoring project is a reusable, vendor-neutral system for recording water meter readings, calculating consumption between successive readings, validating the data for errors, and visualizing trends and anomalies in a dashboard that can be built in Excel or Power BI. The project is designed for industrial and commercial facilities that need a structured way to track water usage across multiple meters and locations without investing in a commercial metering platform. The output is intended for facility managers, sustainability officers, and operations teams who need to understand where water is being used, where usage is unusual, and where opportunities for reduction exist.

The repository is currently in a structured planning phase: the data model, calculation methodology, validation rules, and dashboard plan are all documented, and the supporting templates are being built incrementally. Every design decision is written down before the corresponding file is created, so readers can see not only what the system does but why each choice was made. This makes the project a useful reference for anyone learning how to design a small data system the right way — start with the schema, then the calculation rules, then the validation rules, then the visualization, and only then the dashboard.

The system is intentionally tool-light. Excel and Power BI are evaluated first because they are the most accessible tools for facility teams. Python is recommended only where it adds useful data validation or automation that the spreadsheet cannot do natively. This keeps the barrier to entry low while still leaving room for advanced analysis later.

🔭 Background

Water is one of the most under-managed utilities in industrial facilities. Unlike electricity, which is usually metered at the main incomer and monitored through a utility bill, water is often consumed at many points across a site with only the main meter being read regularly. Sub-meters are frequently installed but rarely read consistently; when they are read, the data is often stored in ad-hoc spreadsheets with no validation, no consistent units, and no clear audit trail. The result is that facility managers usually cannot answer basic questions such as "which area consumed the most water last month?", "is the consumption trend in area X increasing?", or "did the meter in area Y register an anomalous jump that we should investigate?"

This project was built to close that gap in a way that any facility team can adopt without buying new software. It defines a clear data model for water meter records, a calculation methodology that handles cumulative meters correctly (including resets, replacements, and roll-overs), a validation rule set that catches the most common data-entry errors, and a dashboard plan that turns the cleaned data into actionable visualizations. The repository deliberately does not invent consumption readings or claim verified water savings — every number in the project's sample data is clearly labeled as anonymized and synthetic.

✨ Key Features

  • Meter register template — captures the identity of every meter (meter ID, location, area, equipment, unit, install date, serial number) so that consumption records can be joined to a physical asset. This is the backbone of the system: without a clean meter register, none of the downstream analysis is trustworthy.
  • Consumption log template — captures each meter reading with date, time, cumulative reading, units, and a free-text notes column. The schema supports both manual readings and automated logger exports.
  • Cumulative-to-consumption calculation — for cumulative meters, the system computes consumption as the current valid reading minus the previous valid reading for the same meter. The methodology explicitly handles meter resets, replacements, roll-overs, missing readings, and unit changes — all common edge cases that naive spreadsheet calculations get wrong.
  • Validation rule set — flags missing readings, duplicate readings for the same meter on the same date, negative consumption, implausibly large jumps (anomalies), and inconsistent units. Anomalies are flagged as potential issues for investigation, never as confirmed leaks.
  • Daily / weekly / monthly summaries — the system produces time-bucketed summaries that support comparison across meters, areas, and time periods. These summaries are the input to the dashboard.
  • Trend charts and KPIs — the dashboard plan defines a small set of useful visualizations (line charts of consumption over time, bar charts of consumption by area, KPI tiles for total consumption, top consumer, biggest change vs. previous period).
  • Anomaly flags — any reading that breaches a configurable threshold (e.g. consumption more than 3× the rolling average for that meter) is flagged for investigation. The flag is an invitation to investigate, not a confirmed conclusion.
  • Optional target-versus-actual comparisons — where an authorized target exists for a meter or area, the dashboard can compare actual consumption against the target and surface the variance.

🗃 Data Model

The system is built around two core tables:

Table Granularity Purpose
water-meter-register One row per meter Identity + location of each meter
water-consumption-log One row per reading Each individual meter reading event

The two tables are joined on meter_id. The register is the source of truth for what each meter is and where it sits; the log is the source of truth for what each meter has read over time. Any analysis — daily totals, area comparisons, trend charts — starts by joining these two tables.

🧮 Calculation Methodology

For cumulative meters (the most common type), consumption between two successive readings of the same meter is:

consumption = current_reading − previous_reading

The following edge cases are explicitly handled:

  • Meter reset / replacement: if current_reading < previous_reading and a reset / replacement is documented in the notes column, treat current_reading as a new baseline and skip the delta for that interval.
  • Meter roll-over: if current_reading < previous_reading and the meter is documented to have rolled over at its maximum scale, add the maximum scale to the delta.
  • Missing readings: if a reading is missing for a date, no consumption is computed for that interval; the next valid reading computes the cumulative consumption across the gap.
  • Unit changes: if a meter's unit changes (e.g. from gallons to liters), the readings before and after the change cannot be directly compared. The system flags this and requires explicit reconciliation before computing consumption across the change point.

Full details are in docs/calculation-methodology.md.

✅ Validation Rules

The validation rule set is intentionally simple and explainable:

  1. No duplicate readings for the same meter on the same date and time.
  2. No negative consumption unless a documented reset / replacement / roll-over has been recorded.
  3. No missing mandatory fields — meter ID, date, reading, unit are all required.
  4. No inconsistent units — the unit column must match the unit declared in the meter register for that meter.
  5. Anomaly flag — consumption more than 3× the rolling 7-day average for that meter is flagged as a potential issue for investigation, not a confirmed leak.
  6. Date sanity — reading dates must be within a reasonable window of the recording date (e.g. not in the future, not more than 1 year in the past).
